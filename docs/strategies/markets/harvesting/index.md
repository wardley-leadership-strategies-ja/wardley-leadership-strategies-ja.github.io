**プラットフォームのエコシステムを観察し、成功した第三者提供物を買収、複製、統合することで革新を拡大する戦略です。**

> *「他者に自分の提供物の上で開発させ、成功したものを収穫すること。収穫が エコシステム を避けられる場にしないための工夫も含む。」*
>
> - Simon Wardley

## 🤔 **解説**

### 収穫とは何か

収穫は、企業が エコシステム を作り、第三者にその上で新しい 製品 や サービス を 構築 してもらい、そのうち 手応え を得た イノベーション を 感知装置 として観測する戦略です。勝ち筋が見えたら、その企業を買収する、機能を複製する、コアへ深く統合する、などの方法で「収穫」します。

### なぜ使うのか

- **研究開発 の外部化:** 初期革新の高リスク高コストを広い エコシステム へ分散できる
- **市場検証:** 第三者の成功が実際の顧客需要の証拠になる
- **リスク低減:** 勝者が見えてから投資できる
- **俊敏性:** 大企業でも内製だけより速く市場へ追随できる

## 🗺️ **実例**

### Apple App Store

Apple は iOS と App Store を提供し、アプリの大半は 第三者 が作ります。人気アプリや機能 を観察し、懐中電灯、画面録画、キーボード拡張 など、成功した概念を iOS へ取り込みました。

### AWS

AWS は EC2 や S3 の上に顧客が何を 構築 しているかを見ています。共通利用パターンが見えると、それを マネージドサービス として 製品化 し、自社価値を高めます。

### Microsoft と Windows エコシステム

Microsoft は長く Windows 上の 巨大なソフトウェアエコシステム を観察し、ディスク圧縮やファイル検索など、大量のユーザーに必須になった ユーティリティ を OS へ取り込んできました。

### 向くとき

- 活気があり活発なエコシステムを持つプラットフォーム を所有しているとき
- すべてのリスクを自分で負わず、イノベーション speed を上げたいとき
- 市場が速く、どの新機能が当たるか予測しにくいとき

### 避けるとき

- platform がない、または エコシステム が弱いとき
- 開発者コミュニティ に predator と見なされ、trust を壊しそうなとき
- 観測した シグナル に反応する資源や俊敏性がないとき
- acquisition や replication の法務・技術ハードルが高すぎるとき

## 🎯 **リーダーシップ**

### 中核課題

エコシステム との関係管理です。開発者が「良いアイデアは全部盗まれる」と感じれば、プラットフォーム上でイノベーションを起こし しなくなります。収穫しつつも、第三者が 構築 したくなる場を保つ必要があります。

### 必要なスキル

- [コミュニティとエコシステムの育成](/leadership-skills/community-and-ecosystem-stewardship) — 健全な third-party community を育てる
- [戦略的センスメイキング](/leadership-skills/strategic-sensemaking) — 雑音の多い エコシステム から promising イノベーション を見抜く
- [対立管理と外交](/leadership-skills/conflict-management-and-diplomacy) — 収穫時の 反発 を管理する
- [システム思考とバリューチェーン思考](/leadership-skills/systems-and-value-chain-thinking) — 何を core にすべきか見極める

### 倫理面

自分の platform の上で生まれた イノベーション を 利益 に変えるわけなので、倫理的に複雑です。透明性、妥当な対価、収穫後も 繁栄した できる エコシステム の余地が残るかが重要です。

## 📋 **進め方**

1. open で 構築 しやすい platform を作って育てる
2. API 利用量、アプリストアのデータ、コミュニティ参加 など 感知装置 を作る
3. adoption、開発者の関心、revenue の シグナル から勝ち筋を見つける
4. acquisition、replication、partnership のどれで収穫するか決める
5. 公正な価格、または superior integration で収穫を実行する
6. 開発者コミュニティ へ、理由と platform 全体への便益を明確に伝える

## 📈 **成功指標**

- 収穫後も エコシステム の developer 数や app 数が増えているか
- market-validated 機能 をユーザーへ持ち込む速度
- 収穫した 機能 が platform の価値と 粘着性 を高めたか
- acquisition した場合の ROI

## ⚠️ **失敗しやすい点**

### 井戸を毒する

攻撃的すぎる収穫は、developer trust を壊します。

### Sherlocking

third-party app を OS 内蔵で obsolete にすることは、強い 否定的な感情 を生みます。

### シグナル を見落とす

大きな イノベーション を見逃すと、それは強力な 競合 へ育つことがあります。

### 統合失敗

買収・複製できても、統合品質が低ければ ユーザー価値 は出ません。

## 🧠 **戦略的示唆**

### platform は 感知装置 でもある

platform は自社製品の土台であるだけでなく、市場 傾向 を検知し取り込む 感知装置 でもあります。開かれているほど シグナル は増えます。

### 共生関係であるべき

理想的には、エコシステム が イノベーション と市場検証を担い、platform が 規模と流通 を返す共生関係です。寄生的に見え始めると、長期では壊れます。

## ❓ **問うべきこと**

- この収穫をしても 開発者コミュニティ の trust を壊さないか
- 買収 すべきか、自前再現すべきか
- この 機能 は 中核プラットフォーム の一部であるべきほど重要か
- 買収するなら、第三者が作った価値へ 公正な対価 は何か
- 長期で エコシステム の 健全性 と 活気 へどう響くか
