**エコシステム参加者と意思決定権や資産所有を共有し、長期のコミットメントと粘着性を高める戦略です。**

この戦略は Simon Wardley の [On 61 different forms of gameplay](https://blog.gardeviance.org/2015/05/on-61-different-forms-of-gameplay.html) で明示されていませんが、実務ではよく使われるエコシステム統治の一手です。

## 🤔 **解説**

### コミュニティ統治と共同所有とは何か

この戦略は、重要なエコシステム資産に対する control を formalise して共有し、参加者が結果に stake を持つようにするものです。たとえば次の形があります。

- **財団や trust:** 標準、商標、インフラなど共有資産を保有する
- **member council や steering committee:** 予算配分、優先順位、紛争解決を担う
- **shared IP pool や licensing framework:** 共同価値を守りつつ commons を利用可能にする

目的は、「許可された参加」から「権利としての参加」へ移し、参加者が自分のロードマップをこの ecosystem と深く結びつけやすくすることです。

### なぜ使うのか

共有資産が open、stable、fair に保たれると信じられるとき、参加者はその上に build しやすくなります。統治への stake を与えることで trust が増し、深い貢献と長期投資が出やすくなります。結果として採用は速まり、標準は resilient になり、補完的 innovation の流れも太くなります。

### どうやって stickiness を強めるのか

stickiness は、離脱コストと残留便益の両方から生まれます。共同所有はその両方を上げます。

- **Governance lock-in:** 自分たちで作った決定権を捨てる必要がある
- **Asset lock-in:** shared IP、shared roadmap、shared infrastructure が切替コストを上げる
- **Relational lock-in:** council、working group、ritual を通じた reputation capital が移植しにくい

## 🗺️ **実例**

### Linux Foundation

中立財団として重要なオープンソース基盤を統治し、member companies が資金を出しつつ、その上で proprietary offering を構築できるようにしています。

### Cloud Native Computing Foundation（CNCF）

クラウドネイティブ標準やプロジェクトを overseer し、technical oversight committee と段階的ガバナンスで contributor の投資意欲を保っています。

### 仮想例: open data exchange

複数の金融機関が、共有データ schema と API を管理する foundation を作り、member council が upgrade を決め、shared IP pool を維持するケースです。

### 向くとき

- shared infrastructure が単独企業を超える長期投資を必要とするとき
- パートナーが中立性の保証なしには資源を出さないとき
- 標準や shared IP の stable で trusted な home が必要なとき
- reputation と trust が participation 維持の中核にあるとき

### 避けるとき

- 自社優位が tightly controlled proprietary asset に依存しているとき
- ecosystem が小さすぎる、または未成熟すぎて formal governance に見合わないとき
- 規制、税務、法務の複雑性が参加を妨げるとき
- 高速で、最小限の consultation で決める必要があるとき

## 🎯 **リーダーシップ**

### 中核課題

open participation と decisive stewardship の均衡を取り、trusted で fast-moving な ecosystem を保つことです。

### 倫理面

共同所有は participation を広げるために使うべきで、門番を固定化するためではありません。小さな member でも outcome に influence できるか、反競争的 control を隠す器になっていないかが重要です。

## 📋 **進め方**

1. neutral のまま保つべき shared asset を地図化する
2. foundation、cooperative、trust など、制約に合う器を選ぶ
3. voting rights、escalation path、contribution requirements を charter に定める
4. roadmap と budget に責任を持つ member council を置く
5. opportunistic capture を防ぐ shared IP policy を作る
6. neutral operations team に運営、compliance、透明性を担わせる
7. 毎年 governance を見直し、公平さと適応力を保つ

## 📈 **成功指標**

- member participation と contribution volume の成長
- governance channel を通じて決まる roadmap 比率
- partner churn や fragmentation の減少
- shared standard や IP asset の採用拡大
- council vote の time-to-decision

## ⚠️ **失敗しやすい点**

### Governance theatre

foundation や council はあるのに、実権は founding firm が持ち続ける状態です。trust が壊れます。

### Shared IP の停滞

制限が強すぎる、または判断が遅すぎると、contributor が fork や離脱へ向かいます。

### Council gridlock

権限が曖昧なまま council だけ拡大すると、政治化と停滞が起きます。

### 資金の不整合

shared service を期待するのに foundation へ十分出資しないと、統治は脆くなります。

## 🧠 **戦略的示唆**

### 中立性は競争資産になる

市場が interoperability を求めるとき、credible な neutral home は proprietary platform よりも defensible です。競合企業からも投資を引き出せます。

### 共同所有は切替コストを作り替える

共同所有資産から離れることは、decision rights、reputation、shared investment を捨てることです。これは契約ロックインより durable な stickiness になりえます。

### ガバナンス自体がプロダクトの一部

明快な decision rights、透明な vote、信頼できる実行は、それ自体が差別化になります。成熟した governance は ecosystem を build しやすい場にします。

## ❓ **問うべきこと**

- ecosystem 成長のために、どの component は neutral であるべきか
- どこまで decision power を share するのか
- voting や steering rights の条件として何を要求するか
- commons を守りつつ free-riding を防ぐ IP policy はどうあるべきか
- どこは速い判断が必要で、どこは広い合意が必要か
